1. REQUIREMENTS                           *ghostty-smart-splits-requirements*

Neovim 0.11+, smart-splits.nvim, Ghostty 1.3+ on macOS, and macOS Automation
permission. Run Neovim locally inside Ghostty. Configure Ghostty's nvim key
table before starting Neovim; the ready-to-copy configuration is in
examples/ghostty.conf.

2. SETUP                                         *ghostty-smart-splits-setup*

SMART-SPLITS V2

Configure smart-splits normally, then call setup() once at startup with the
Neovim pane focused:
>
  require('smart-splits').setup({}) -- Existing options and mappings.
  require('ghostty-smart-splits').setup({})
<
The v2 setup preserves existing smart-splits options and sets
`multiplexer_integration = 'ghostty'` and `at_edge = 'stop'`. It returns false
when the session is unsupported; terminal attachment and key-table activation
continue asynchronously after setup.

SMART-SPLITS V3 (EXPERIMENTAL)

Use smart-splits.nvim's `v3` Git ref and select the backend:
>
  require('smart-splits').setup({
    mux = { backend = 'smart-splits-backend-ghostty' },
    move = { at_edge = 'stop' },
  })
<
Do not call the v2 root module's setup() with v3. Core activates the selected
backend during setup; start Neovim with its Ghostty pane focused. The v3
protocol may change before release.

CONFIGURATION

`key_table` is the name of the Ghostty key table used while Neovim is active.
It defaults to `nvim` and must be a non-empty string. Changing it to a
different name while it is claimed is an error; release it first.

`bridge` is a boolean, default false. When true, actions and pane lookups
prefer the persistent bridge and fall back to osascript when it is
unavailable. When false, both use only osascript, even if the binary exists.

Use the v2 root module or the v3 backend module, depending on the integration:
>
  -- v2
  -- If navigation feels slow, build the bridge and set bridge = true.
  require('ghostty-smart-splits').setup({ key_table = 'editor', bridge = false })

  -- v3: configure the backend before smart-splits setup.
  require('smart-splits-backend-ghostty').setup({
    key_table = 'editor',
    bridge = false, -- If navigation feels slow, build the bridge and set true.
  })
<
Configuration does not run AppleScript, start a bridge, attach to Ghostty, or
register autocommands. Disabling the bridge stops an existing bridge immediately.
Enabling it takes effect on the next attachment or action. In v2, the root
setup continues with attachment and activation; in v3, core activates the
selected backend.

setup() merges over the current options: a call that names one option leaves
the rest alone, so the bridge can be toggled at runtime without repeating
key_table. An unknown option name is an error rather than a silent no-op.
Call config.reset() to restore every default.

In local measurements, bridge actions took about 30 ms versus about 130 ms
through per-call osascript; results vary by machine.

The bridge is a persistent Swift process that reuses compiled AppleScript to
reduce the overhead of sending actions to Ghostty.

The optional bridge requires Xcode Command Line Tools. Build it from the
plugin directory, then set bridge = true:
>
  make bridge
<
This creates bin/ghostty-smart-splits-bridge. A plugin manager can run this
command on install/update; setup() never compiles it. Each Neovim instance owns
one bridge and stops it on exit. Only the initial terminal lookup uses
osascript, asynchronously, before the bridge is running.

smart-splits v2 brackets each pane move with a terminal lookup, so one move is
three Ghostty requests. All three take the bridge when it is enabled.

3. API                                             *ghostty-smart-splits-api*

require('ghostty-smart-splits').claim_keys()
    Push the configured Ghostty key table if it is not already claimed.

require('ghostty-smart-splits.config').reset()
    Restore every option to its default. setup() merges rather than
    replaces, so this is the only way back to the defaults.

require('ghostty-smart-splits').release_keys()
    Pop the table claimed by this instance. Keys are also released on
    VimSuspend and VimLeavePre, and claimed again on VimEnter and VimResume.

:checkhealth ghostty-smart-splits
    Check local prerequisites, bridge preference, binary path, and running
    status without starting the bridge. With v3, :checkhealth smart-splits
    also includes backend diagnostics.

The underscore names ghostty_smart_splits and ghostty_smart_splits.health
remain deprecated aliases for the dashed module and health names.

4. LIMITATIONS                            *ghostty-smart-splits-limitations*

macOS only. Action AppleScript calls are synchronous and time out after one
second.
The initial Ghostty terminal comes from the focused pane and the lookup is
asynchronous. Later actions keep using that terminal instead of following
focus changes.
A failed lookup is retried when Neovim next regains focus, which is when the
Automation prompt has been answered and is also proof the focused pane is
still ours. After five failures the plugin stops trying and warns once.

Do not stack another Ghostty key table above this one while Neovim is active.
If a crash or config reload leaves stale state, the Ghostty action
deactivate_all_key_tables can recover it, but clears every table.

Native performable:goto_split bindings can give Ghostty priority. This plugin
is for Neovim-first navigation.
